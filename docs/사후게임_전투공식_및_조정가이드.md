# 사후게임 전투 공식 및 조정 가이드

> 기준일: 2026-09-19
>
> 대상: 운영 Battle registry의 `stat-boss`, `data-sphinx`, `control-boss`, `xr-egg-trials`
>
> 원칙: 이 문서의 **현재값**은 구현과 배포 설정을 설명한다. **권장 검토값**은 아직 확정된 게임 규칙이 아니다.

## 1. 공통 연결

네 콘텐츠는 `data/battles.json`에서 정적으로 등록되고, 서로 다른 학과 미니게임 5종을 모두 완료했을 때 함께 열린다. 로그인 계정의 `/api/me.completedGameIds`와 현재 브라우저의 로컬 완료 ID를 합쳐 판정하며, 같은 게임을 여러 번 클리어한 횟수로는 대신할 수 없다.

각 Battle은 아래 lifecycle을 동일하게 구현한다.

```text
init(config, { signal })
→ start({ attemptId })
→ pause(reason) / resume()
→ onComplete(attemptId, candidate)  // attempt당 정확히 한 번
→ restart({ attemptId }) 또는 destroy()
```

결과의 `sessionId`, `battleId`, 실제 플레이 시간은 공용 Battle host가 붙인다. 개별 모듈은 `CLEAR` 또는 `FAIL`, 점수, 실패 사유, 지표만 후보 결과로 반환한다. 현재 Battle 결과는 화면에만 표시하며 D1 결과·랭킹·스탯 포인트에는 저장하지 않는다. 서버 권위 판정과 보상 정책이 확정되기 전에 클라이언트 결과로 포인트를 지급하지 않기 위한 의도적인 제한이다.

### 1.1 온라인 presence·보스방 연결 경계

- 로그인 사용자는 같은 origin의 `/api/postgame/socket` WebSocket에 연결한다. Worker가 `Origin`과 session을 확인한 뒤 단일 SQLite-backed Durable Object coordinator로 넘긴다.
- coordinator는 `entry-field`·`plaza` presence와 보스 3종의 공개 방 디렉터리를 관리한다.
- 생성자는 정규화 후 1~32자의 공개 방 이름과 1~5명 정원을 정한다. 방장만 1명 이상인 방을 원하는 시점에 수동으로 시작할 수 있고, 정원이 차도 자동 시작하지 않는다. 방장이 나가면 남은 참가자에게 권한을 위임하며 같은 계정의 여러 연결은 좌석을 중복 점유하지 못한다.
- WebSocket Hibernation attachment에는 연결별 계정 키·공개 플레이어 ID·구역·위치·방 상태를, Durable Object storage에는 방 이름을 포함한 공개 방 목록을 저장한다.
- D1은 계정·스탯·session·사전게임 결과를 저장하며, 고빈도 위치나 보스방 상태에는 사용하지 않는다.
- 게스트와 WebSocket 장애 상황에서는 온라인 방 없이 기존 솔로 전투로 직접 들어갈 수 있다.

방을 시작하면 참가자들에게 같은 `battleId`·`roomId`·`seed`·`startedAt`·`roster`를 보내 같은 전투 route로 이동시킨다. 그러나 현재 세 보스의 이동·공격·피격·보스 HP·phase·결과는 각 브라우저가 독립적으로 계산한다. 공통 시작 payload는 서버 권위 협동 전투나 공유 HP 구현을 뜻하지 않는다.

## 2. 계정 스탯 변환

원본 위치는 `js/battle/player-config.js`이다. D1의 계정값은 공격·방어가 `0`부터 시작하고 HP는 `100`부터 시작한다. Battle 내부의 보너스 없는 기준은 `1/1/1`이므로 한 번만 다음처럼 변환한다.

```text
전투 공격 스탯 A = D1 attack + 1
전투 방어 스탯 D = D1 defense + 1
전투 체력 스탯 H = 1 + max(0, D1 hp - 100)
보너스 포인트 B(S) = max(0, S - 1)
```

게스트는 `A=1, D=1, H=1`이다. 사용자 이름·이메일·Google ID는 Battle 모듈에 전달하지 않는다.

## 3. 콘텐츠별 현재 공식

### 3.1 데이터 스핑크스

설정은 `data/battle/data-sphinx.json`, 판정은 `js/battle/postgame/bosses/data-sphinx/encounter.js`와 `config.js`에 있다.

```text
문제 제한 시간 = 5,000ms
O 판정 = 캐릭터 중심 x < 경기장 너비 / 2
X 판정 = 캐릭터 중심 x > 경기장 너비 / 2
정중앙 = 미선택(시간 초과와 같은 피해)

정답: 보스 HP -= 10
오답 또는 미선택: 플레이어 HP -= 20
초기 보스 HP = 100
초기 플레이어 HP = 100
문제은행 = 이화여대 20개 + 일반·IT 상식 20개, 총 40개
도전당 출제 = 문제은행을 섞어 중복 없이 우선 10개 선택
클리어에 필요한 정답 = 10개
문제 사이 결과 표시 = 2,000ms
사망 결과 표시 = 1,000ms
```

현재 MVP는 매 시도마다 40문항 문제은행에서 10개를 무작위로 먼저 뽑는다. 정답 10개를 맞히면 보스 HP가 0이 된다. 오답·미선택 문항은 남은 문제은행의 비중복 예비 문항으로 보충되어 다음 정답으로 만회할 수 있고, 5회 누적되면 플레이어 HP가 0이 되어 `PLAYER_DEAD`로 실패한다.

계정 공격·방어·HP는 이 전투의 고정 퀴즈 피해에 적용하지 않는다. 점수와 보상도 현재 `null`이다.

현재 문항은 병합된 행사 후보 문제은행이며, 학교 운영 정보·법령·연도처럼 바뀔 수 있는 항목은 행사 전에 다시 검수해야 한다. 교체 방법과 검수 기준은 [`data-sphinx-question-sources.md`](./data-sphinx-question-sources.md)에 기록했다.

### 3.2 스탯 보스

설정은 `data/battle/stat-boss.json`, 수치 공식은 `js/battle/postgame/bosses/stat-boss/stats.js`, 난이도는 `difficulty.js`, 진행 판정은 `encounter.js`에 있다.

```text
플레이어 반격 피해 = 10 × (1 + B(A) × 0.05)
플레이어 최대 HP = 100 + B(H) × 10
회피 실패 시 피해 = max(1, 보스 공격력 10 - B(D))

1~5인 보스 총 HP = 1,000
경직 시간 = 1,400ms
전체 제한 시간 = 없음
경직 1회당 플레이어 1명당 유효 반격 = 1회
결과 점수 = round(누적 반격 피해)
```

기본 스탯 1인 플레이에서는 10 피해의 반격 100회가 필요하다. 기존 120초 제한을
유지하면 수학적으로 클리어가 불가능하므로 제한 시간만 제거했다. 설정상 방 정원과
무관하게 보스 총 HP 1,000을 유지한다. 다만 현재 room roster는 전투의 `players` 배열로
합쳐지지 않으므로 각 브라우저는 로컬 플레이어 한 명의 전투를 실행하고, 여러 참가자의
반격 피해를 하나의 보스 HP에 합산하지 않는다.

시간에 따라 패턴 후보와 첫 예고 시간이 바뀐다.

| 경과 시간 | 첫 예고 | 패턴 후보 |
| --- | ---: | --- |
| 0초 이상 15초 미만 | 1,500ms | 단일 저격 |
| 15초 이상 40초 미만 | 1,200ms | 단일 저격, 광역 확산, 좌우 스윕 |
| 40초 이상 | 800ms | 앞의 3종, 다중 락온, 연속 콤보 |

좌우 스윕·연속 콤보의 두 번째 이후 step 예고는 `max(400ms, 첫 예고 / 2)`이다. 광역 확산의 안전 칸은 현재 위치에서 행·열 각각 1칸 이내인 후보 중 1~2칸이다.

파티 HP 배율은 사용하지 않고 1~5인 방 모두 총 HP 1,000 설정을 사용한다. 전투 core는 여러 `players`가 주입되면 다중 락온을 처리할 수 있지만, 현재 Battle host는 각 클라이언트의 로컬 플레이어 한 명만 전달한다. 원격 좌표·피격 동기화 전에는 온라인 방 인원만으로 다중 락온이 활성화되거나 실제 팀 전투가 되지 않는다.

### 3.3 컨트롤 보스

설정은 `data/battle/control-boss.json`, 공식은 `js/battle/postgame/bosses/control-boss/config.js`, 전투 진행은 `encounter.js`에 있다.

```text
공격 1회 피해 = 40 × (1 + B(A) × 0.05)
최대 HP = 100 + B(H) × 10
최종 피격 피해 = max(1, 원본 피해 - B(D) × 1)

보스 HP = 1,000
실드 = 500
공격 가능 거리 = 130px
```

기본 스탯의 실드 파괴에는 `ceil(500 / 40) = 13회` 공격이 필요하다. 전투는 아래 순서로 반복된다.

1. 실드 단계: 첫 탄환은 0.6초 뒤, 이후 1.3초마다 속도 240px/s의 탄환을 발사한다. 원본 탄환 피해는 15다.
2. 즉사기 단계: 3초 안에 중앙 엄폐 구역에 들어가 있어야 한다. 밖에 있으면 즉시 실패한다.
3. 발판 단계: 30초 안에 3×3 발판 중 표시된 4개를 순서대로 밟는다. 2개는 낙사 칸이다. 틀린 발판은 진행 순서를 0으로 되돌리고 1초 경직을 준다. 충격파는 2초 후 시작해 4.5초 간격으로 발생하며 원본 피해는 25다. 이 단계에서 보스는 초당 최대 HP의 1%, 즉 초당 10 HP를 회복한다.
4. 그로기 단계: 발판 성공 즉시 보스 최대 HP의 20%, 즉 200 피해를 주고 10초 동안 직접 공격할 수 있다. 쓰러뜨리지 못하면 실드 단계로 돌아간다.

발판 진입 시 보스가 최대 HP라면 기본 공격으로 그로기 중 남은 800 HP를 없애는 데 `ceil(800 / 40) = 20회`가 필요하다. 현재는 공격 쿨다운이 없고 각 키·버튼 press를 한 번의 공격으로 센다. 점수와 보상은 `null`이다.

### 3.4 X알 무작위 챌린지

설정은 `data/battle/xr-egg-trials.json`, 규칙은 `js/battle/postgame/challenges/xr-egg-trials/rules.js`, lifecycle과 화면은 같은 디렉터리의 `index.js`에 있다.

한 attempt를 시작할 때 세 시험 중 하나를 같은 확률로 선택한다.

- 가위바위보: 한 번 선택한다. 상대도 세 손 중 균등 무작위다. 이겨야만 CLEAR이고 비김도 실패다. 상대가 균등하다는 전제에서 선택별 이론상 CLEAR 확률은 `1/3`이다.
- 카드 짝맞추기: 기호 5종을 두 장씩 섞은 10장이다. 처음 1,000ms 공개하며, 3쌍을 찾으면 CLEAR다. 틀린 한 쌍마다 기회가 1 감소하고 5회 소진 시 실패한다. 오답 카드는 700ms 뒤 다시 닫힌다.
- 연타: 10,000ms 안에 40회 입력하면 CLEAR다. 화면 버튼과 공용 `Space/Enter` 입력은 같은 카운터를 사용한다.

표시용 점수는 아래와 같지만 서버 랭킹에는 저장하지 않는다.

```text
가위바위보 = 승리 100, 실패 0
카드 = 맞힌 쌍 × 100 + 남은 기회 × 10
연타 = 입력 횟수 × 10
```

기존 필드 프로토타입의 성공 시 `스탯 +10`은 제거했다. 어떤 스탯을 어떤 빈도로 지급할지, 반복 파밍을 허용할지가 정해지지 않았기 때문이다. 현재 운영본에서는 입장 필드를 실제로 이동한 거리에 따라 X알이 랜덤 출현하고, 접촉하거나 직접 선택하면 `xr-egg-trials`를 실행한다. 광장에서는 랜덤 출현 거리를 누적하지 않는다.

## 4. 무엇을 어디서 바꿀 수 있는가

### 데이터 파일만 바꾸면 되는 값

| 콘텐츠 | 설정 경로 | 주요 키 |
| --- | --- | --- |
| 데이터 스핑크스 | `data/battle/data-sphinx.json` | `timeLimitMs`, `bossMaxHealth`, `damagePerCorrect`, `playerDamagePerWrong`, `resolutionDelayMs`, `quizList` |
| 스탯 보스 | `data/battle/stat-boss.json` | `bossBaseHp`, `bossAttack`, `staggerDurationMs`, `timeLimitSec`; 필요 시 `balance.baseDamage`, `balance.damageCoefficient`, `balance.baseHp`, `balance.hpPerPoint` |
| 컨트롤 보스 | `data/battle/control-boss.json` | `boss.*`, `player.*`, `gimmick.*` |
| X알 | `data/battle/xr-egg-trials.json` | `selectionMode`, `trialIds`, `cardMatch.*`, `mash.*` |

JSON을 바꾼 뒤에는 반드시 `npm run check:release`를 실행한다. 숫자를 한 번에 여러 개 바꾸면 원인을 비교하기 어려우므로 한 변수씩 수정하고 아래 기록표에 결과를 남긴다.

### 코드 변경이 필요한 규칙

- 스탯 보스의 시간 구간, 패턴 후보, 다단 step 배율, 광역 안전 칸 거리
- X알 가위바위보의 무승부 처리와 세 시험의 점수 공식
- 컨트롤 보스 공격 쿨다운 추가
- 세 보스방 결과의 D1 저장, 랭킹·스탯 보상
- coordinator가 전달한 공통 seed의 결정론적 소비, 전투 상태 복제와 서버 권위 피격·결과 판정
- 진행 중 연결 복구, 방 roster 변동, 팀 결과와 개인 기여 처리
- 네트워크 단절 시 결과를 재전송하는 outbox와 게스트 기록을 로그인 계정에 합칠지에 대한 정책
- 자유 이동 필드 X알의 1회성·반복 보상 정책

| ---: | --- | --- | --- | --- | --- |
| 1 | 필수 | 데이터 스핑크스 문제 사실·정답 검수 | 5초 제한, 40문항 문제은행에서 도전마다 비중복 10개 우선 출제 | `data/battle/data-sphinx.json > quizList` | 행사 직전 시점 의존 문항을 재검수하고 문구·정답표 최종 승인 |
| 2 | 필수 | 데이터 스핑크스 합격 허용치 | 정답 10개면 클리어, 오답은 예비 문항으로 만회 가능, 오답·미선택 5회면 실패 | `questionsPerAttempt`, `bossMaxHealth`, `damagePerCorrect` | 10회 이상 플레이해 읽기 시간·오답 허용치가 의도와 맞는지 측정 |
| 3 | 필수 | 컨트롤 보스 10초 연타량 | 기본 스탯은 그로기 중 20회 공격 필요, 쿨다운 없음 | `player.baseAttackDamage`, `boss.groggyDurationSec`; 쿨다운은 코드 | PC·실기 모바일 모두 의도한 반복 횟수 안에 클리어 가능 |
| 4 | 필수 | 컨트롤 보스 화면·충돌 | 세로 450×800 경기장, 즉사·낙사 포함 | `world.*`, `gimmick.*` | 작은 모바일에서 발판 번호·엄폐·탄환이 구분되고 불공정 즉사 없음 |

## 6. 구현 감사 결과

- 운영 loader는 published 5종 module key만 정적 allowlist로 허용한다. 콘텐츠 JSON으로 임의 JavaScript 경로를 실행할 수 없다.
- 새 Data Sphinx와 Control Boss는 공용 캐릭터 이동·모바일 조이스틱을 사용한다. X알은 자체 버튼 UI를 쓰되 공용 입력의 확인 동작과 연결한다.
- 결과 overlay, 재도전, 배틀 목록 이동은 host 한 곳에서 처리한다. 개별 모듈이 전역 modal을 중복 생성하지 않는다.
- 일시정지·탭 숨김은 게임 시간과 움직임을 멈추며, 재시작·화면 이탈·Abort 시 loop, timer, listener, DOM을 정리한다.
- 기존 `js/battle/postgame/bosses/data-sphinx.js`, `js/minigames/after_controlboss/`, `js/battle/minigames/` 전역 prototype은 참고용으로 남지만 production `dist/`에서는 제외한다.
- 순차 보스 진행은 의도적으로 두지 않았다. 로그인 presence·공개 방·공통 시작 payload는 연결했지만 보스의 실제 전투 판정과 사후게임 보상은 아직 공유·서버 권위로 연결하지 않았다.
